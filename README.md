# Splat Arena

An original browser paintball game:
**Vite + TypeScript + three.js + pmndrs/postprocessing** in the browser, and a small **Node WebSocket server** for multiplayer.

The 3D models (bunkers, marker, player with animations) are generated by a script in this repo, so everything here
is original and you can read the whole thing in an afternoon.

**Play it:** https://splat-arena.fly.dev/ (the first load after a quiet spell takes a few seconds while the server wakes up).

## Run it

Needs Node 20.19 or newer.

```powershell
npm install
npm run dev
```

Open http://localhost:5173. `npm run dev` starts both the client (Vite, port 5173) and the game server (port 8787).
Open a second browser window to play against yourself: the server puts the next player on the other team.

**How a match works:** once both teams have a player, everyone is put back in their start box for a 3-second countdown.
Then the point is live: if you're hit you're out until the point ends, and you walk off the field with your marker up (the game walks you to the nearer side line, round the bunkers). Then you watch a teammate who's still in, over their shoulder: Space (A on a controller) switches to the next one. Between points (8 s) the camera cuts between a few shots, like a broadcast: the winners, the bunker that took the most paint, a sweep over the field. Eliminate the whole other team to win the point.
First team to 5 points wins the match. While a team is empty it's warm-up: you respawn a few seconds after being hit.
The game opens on the main menu, flying slowly around the field. Pick a name (it shows over your head, in the kill
feed and on the scoreboard), then **Play online** to join the match. The menu shows how many are playing. **Practice**
plays offline against three strafing targets on the field you pick. Esc (or Start on a controller) pauses: Resume,
Settings, Controls, or Leave match. Online, you're still in the match while paused.

**Fields** (`shared/maps.ts`). Pick one with the arrows at the top of the main menu: it shows behind the menu,
Practice plays on it, and Play online votes for it. Online, everyone gets a vote: the pause menu has a card per field with its layout drawn from above, and after a match the cards come up on screen for 12 s (press a card's number to vote). When every player wants the same other field it switches at the next break between points, and otherwise the field with
the most votes comes up after the match (the next one in turn if nobody voted). `MAP=<id>` on the server plays one
field only, with no vote.

| field | size | |
|---|---|---|
| Arena (`arena`) | 46 × 30 m | the original compact speedball field |
| Tournament (`tournament`) | 54 × 36 m | big symmetrical inflatable layout: a snake wall down one side, triangles down the other, a centre diamond |
| Beach (`beach`) | 52 × 32 m | sand and surf: beach huts, a lifeguard tower, dunes, driftwood and an upturned boat |
| Woods (`woods`) | 90 × 60 m | a forest: about a hundred trees, boulders, fallen logs, pallets and cable spools |
| Moonbase (`space`) | 48 × 30 m | the moon: planets for bunkers, moonballs with comet tails, astronaut suits and a star burst for every out |

Each half is the mirror image of the other, so neither team has an advantage.

**Markers** (`shared/fire.ts`). How the trigger works is part of the game, so everyone on a server plays the same one.
Pick it under the field on the main menu: Practice plays it, and Play online votes for it (change your vote from the
pause menu). A mode more than half the players vote for takes over after the point. `FIRE_MODE=<mode>` on the server
plays one mode only, with no vote. The server holds every shooter, bots included, to the mode's rate.

| marker | |
|---|---|
| Ramp (`ramp`, the default) | one ball per pull; three quick pulls in a row (each within 0.3 s) and you can hold the trigger for 10 a second, until you let go |
| Semi-auto (`semi`) | a mechanical marker: one ball every time you pull, never more than 10 a second. Holding does nothing |
| Pump (`pump`) | one ball, then a half-second pump stroke before the next (pulls during it are lost). A 20-ball tube |

- **Playing alone?** The server fills both teams with bots (3 a side by default), so you can play a match on your own.
  A friend who joins takes a bot's place.
- **No server running?** Practice works without one, and if the server drops mid-match you practise until it's back.
- **Slow machine?** Add `?low` to the URL to turn off shadows, bloom and anti-aliasing. Phones and tablets start
  that way; add `?high` to turn it back on.
- **Voice chat?** If the server has a voice server set up (docs/DEPLOY.md), hold **V** (d-pad up on a controller, the
  Talk button on a phone) to talk to your team. The microphone only opens while you hold it, and the browser asks
  first. Settings has a volume slider and an off switch, and Players in the pause menu mutes anyone.
- **Controller?** Connect one (Bluetooth or USB) and press any button: the main menu says when it's found. The d-pad
  or left stick moves through the menus, A picks and B goes back. On a phone, clip it on or pair it, open the game in
  the phone's browser, turn the phone sideways and pick Play online. "Add to home screen" opens it fullscreen like an app.
- **Phone with no controller?** Turn it sideways and play with the on-screen controls: put your left thumb down
  anywhere on the left half and drag to move (push well out to sprint), drag on the right half to aim, and hold Fire
  to shoot (you can keep aiming by dragging on it). Jump, Crouch, Lie (tap to stay down, or hold) and Reload are round
  the Fire button. They hide while a controller is connected.
- **Check the server works:** `npm test` runs the wire-format round-trip checks, the controller checks and the map
  checks (every field: bunkers inside the lines, start positions clear, halves mirrored, paint stops on every bunker,
  players kept out, bots can path across), then `npm run test:server`, which starts its own servers, plays a point
  between two fake players, checks lag compensation with a fake 150 ms player, then checks that bots fill the teams,
  move, shoot and finish a point. `npm run test:maps -- --bots` also has bots play a point on every field.

| Controls | |
|---|---|
| Mouse / click | aim / fire (one ball per pull; on a ramp marker, three quick pulls then hold for 10 a second) |
| WASD, Shift | move, sprint |
| Space, C, Z | jump (you can jump onto the low walls), crouch, lie down and crawl. Tap C or Z to stay down until you tap again (or jump), or hold it to stay down only while held |
| R | reload (200-ball hopper, or a 20-ball tube on a pump) |
| Tab (hold) | scoreboard |
| V (hold) | talk to your team (voice chat) |
| H | first person / third person (over the shoulder) |
| Q | third person: look over the other shoulder (Settings also has Auto: the side you strafe or peek toward) |
| Esc | pause (menu) |

| Controller | |
|---|---|
| Left stick | move (how far you push sets your speed); click it to sprint until you stop |
| Right stick | aim, slowed a little while your crosshair is on an opponent; click it for first / third person |
| RT (or RB) | fire |
| A / B / X | jump / crouch (tap B) or lie down (hold B; tap again to get up to a crouch) / reload |
| LB (hold) | sprint |
| Select (hold) | scoreboard |
| Start | pause (menu); on a phone there's also a Menu button |
| D-pad up (hold) | talk to your team (voice chat) |
| D-pad left / right | third person: look over your left / right shoulder |

Look speed, invert Y, vibration, volume, graphics quality, the view (first or third person) and the shoulder are under
Settings and saved in your browser. In third person the camera sits over your shoulder and pulls in when a bunker is
behind you; paint still flies from your marker to whatever the crosshair is on. Q (or the d-pad) slides it over to the
other shoulder, for peeking out of the other side of a bunker. On Auto it follows the way you strafe, and moves off a
shoulder that's right up against a bunker if the other side is clear. `npm run test:input` checks
the deadzones, response curve and buttons.

## How it's put together

```
shared/       code BOTH sides run, so they agree
  protocol.ts   every network message, typed
  codec.ts      compact binary encoding for snapshots, acks, paintballs and input frames
  maps.ts       every field: size, bunker layout, look (ground, sky, scenery)
  field.ts      the field being played: bunker shapes, spawn points, footprint maths
  sim.ts        movement, paintball flight, collision (no physics engine needed)
  walkoff.ts    the way off the field for out players (a distance map round the bunkers)
  netsim.ts     fake latency and packet loss for development and tests
server/
  index.ts      authoritative game server: simulates paintballs, decides hits, runs the match, sends snapshots
  voice.ts      voice chat tokens for the LiveKit media server (who's in the room, on which team)
  bots.ts       server-side bots: navigation grid + A*, cover spots, aim with reaction delay and error
  rtc.ts        WebRTC data channel to each browser, for snapshots, acks and input (UDP, never resent)
  smoke-test.ts headless end-to-end checks (starts its own servers)
  map-test.ts   checks every field's layout, collision and bot navigation
  test-client.ts fake players for the tests: join, walk with real input frames, see others like a browser
  net-measure.ts how play holds up with latency and packet loss (npm run measure:net)
  codec-test.ts round-trip checks for the binary wire format
scripts/
  build-assets.ts builds the marker and player models from code (npm run assets)
  blender-assets.ts exports the Blender-made models (npm run assets:blender, docs/BLENDER.md)
art/            sources for the Blender-made models (build scripts and .blend files) and their rules
public/models/  the models (meshopt-compressed glTF, ~240 KB total)
src/          the browser game
  main.ts       game loop (fixed 120 Hz physics step), shooting, wiring
  toon.ts       the arcade look: toon (banded) materials and the ink outline pass
  render.ts     WebGLRenderer + postprocessing (bloom, vignette, tone mapping, SMAA)
  world.ts      builds the current field: sky, lights, ground, boundary, bunkers, scenery
  player.ts     first-person controller + the gun on screen
  input.ts      keyboard + mouse (pointer lock) and controllers, combined into actions; phone start
  touch.ts      on-screen controls for phones: move stick, aim by dragging, Fire / Jump / Crouch / Lie / Reload
  gamepad.ts    controllers: deadzones, aim curve, buttons, rumble (gamepad-test.ts checks it)
  paintballs.ts all balls in flight, drawn as glowing streaks (three InstancedMeshes); near-miss whizzes
  fx.ts         paint splat decals + droplet bursts
  models.ts     loads the models (with a loading bar); falls back to code-drawn shapes if they fail
  avatars.ts    other players: the animated model, driven by speed / crouch / lying down / eliminated / shots
  net.ts        WebSocket client + snapshot interpolation
  netstats.ts   development network overlay (?net, ?lag=, ?loss=)
  fastlink.ts   the browser's end of the data channel
  hud.ts        HTML overlay (no UI framework)
  menu.ts       main, pause, players, settings and controls menus; controller navigation
  voice.ts      team voice chat: push-to-talk, team/everyone channels, speaking indicators, muting
```

**Who decides what:**

- **Your movement:** your browser sends its keys and aim to the server as small fixed-length steps. The server runs
  the same movement code (`shared/sim.ts`) on them and decides where you are, so nobody can teleport or speed up.
  Your browser predicts the same steps locally, so moving feels instant, and quietly corrects itself if the server
  disagrees (`src/prediction.ts`).
- **Paintballs:** your browser draws them the instant you click. The server *also* flies them using the same `shared/sim.ts` code, in the same fixed steps, and is the only one that decides eliminations.
- **Paint colours:** paint comes in bright fills (yellow, lime, pink, orange, cyan, purple), not the team colours. Each
  field gives each team a different one (`theme.paint` in `shared/maps.ts`). Look only.
- **Paint speed:** shots leave at 280 ft/s on average, each one up to 2% faster or slower (picked from the firing
  point, so the shooter and the server agree without sending it); drag slows them down, so aim a little high at range.
- **Bounces:** paint that hits the ground always breaks. Paint that hits a bunker at a shallow angle (under about 30°)
  usually bounces off; a squarer hit on a bunker breaks. A bounced ball flies on and can
  still eliminate someone. Whether it bounces is a roll of the dice, but every machine rolls the same dice: each ball's
  random numbers start from a hash of the point it was fired from, which the shooter, the server and every other browser
  all know. Inflatable bunkers wobble when hit (`src/world.ts`), wood and rock don't. Paint can bounce off players too:
  most hits break, but a glancing one often skips off (about 5 in 100 hits overall), and that player plays on. The server
  decides, and the feed says "bounce, plays on".
- **Event feed:** besides who hit whom, the corner feed calls doubles and triples, eliminations off a bounce, paint
  bouncing off a player, and the last one standing on a team. Your own eliminations in a row pop up as a streak.
- **Other players:** drawn 100 ms in the past, blended between the server's snapshots, so they move smoothly instead of jumping 20 times a second.
- **On the wire:** the messages sent many times a second (snapshots, your position acks, paintballs, your input) are
  packed into small binary frames (`shared/codec.ts`): positions to the centimetre, angles to a few thousandths of a
  degree. In a 6-on-6 match that's about 5 KB/s down and 2 KB/s up per player, versus about 32 and 5.5 as JSON.
  Everything else (joining, names, eliminations) stays JSON so it's easy to read in the browser's network tab.
- **Two connections:** snapshots, acks and input frames go over a WebRTC data channel straight to the game server when
  the browser can reach its UDP port (`server/rtc.ts`, `src/fastlink.ts`). It never resends, so a lost packet is just
  one skipped snapshot instead of a TCP stall that freezes everyone for a round trip. Input frames repeat the last few
  in every packet, so a lost one costs no input. Everything else, and everything when UDP is blocked, goes over the
  WebSocket. See docs/DEPLOY.md for opening the port.
- **Lag compensation:** because of that, and your ping, you're aiming at where people *were*. The server keeps a second
  of everyone's positions and tests your paintballs against targets as they were on your screen (your ping + 100 ms
  ago, at most 300 ms), so a shot that hits on your screen hits on the server too.

In development, `window.__game` in the browser console exposes the player, network, scene and so on. URL options
(development builds only):

- `?lag=150` fakes 150 ms of round-trip latency, so you can see how prediction copes.
- `?loss=2` loses 2% of messages each way, the way a WebSocket's TCP connection does: a lost packet is resent about a
  round trip later and everything behind it waits (`shared/netsim.ts`). Combine it with `?lag=`.
- `?net` shows a network overlay (it's also on with `?lag=` or `?loss=`): snapshot gaps over 100 ms, how often other
  players froze because the 100 ms interpolation buffer ran dry, and how often the server corrected your position.
- `?rtc=0` stays on the WebSocket instead of opening a data channel, to compare the two.
- `?hitboxes` outlines where the server tested each hit (after rewinding for lag).

`npm run measure:net` plays a fake player at 50 and 150 ms with 0 to 5% loss and prints a table of the same numbers
(`npm run measure:net -- 150 2 60` for one run: lag, loss, seconds; add `--rtc` to measure over a data channel).

## Where to take it next

Roughly in order of payoff:

1. **Hand-made art.** Most models are built by `scripts/build-assets.ts`. Detailed ones come from Blender through
   `npm run assets:blender` (see docs/BLENDER.md, which also covers working with Claude through the Blender MCP server).
   To replace a code-made model, make it in Blender with the node names listed at the top of that script. A skinned
   character with mocap-style animations would be the biggest upgrade.
2. **More modes.** Capture the flag, an attack/defend variant, and so on (rounds are already in).

## Deploying

The `Dockerfile` builds one small image that runs the game server and serves the website on the same port:

```powershell
docker build -t splat-arena .
docker run -p 8080:8080 splat-arena
```

Put it on a VPS or container platform behind TLS (WebSocket upgrades must pass through) and set `ALLOWED_ORIGINS` to
your site's address. It has a `/healthz` endpoint and shuts down cleanly on `SIGTERM`. To host the website separately,
build with `VITE_SERVER_URL=wss://your-server`. All settings are environment variables. The full guide is in
[docs/DEPLOY.md](docs/DEPLOY.md), and every setting with its default is in `.env.example`.

The live game runs on Fly.io from `fly.toml`: `fly deploy --ha=false` ships a new version.
